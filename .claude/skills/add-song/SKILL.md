# Добавление песни

Вход: `$ARGUMENTS` — файл записи и, возможно, ссылка на официальное видео. Запись с YouTube не скачивать. Текст, перевод и тайм-коды находят по маршруту, а не по памяти.

Маршрут один: `docs/methodology/README.md`. Файл стадии открывайте, когда `song-status` на него указал. После каждого шага:

```bash
npm run song-status -- <slug>
```

Напечатана одна команда. Выполните её. Если команда снова `song-status`, абзац над ней — ручная правка файлов.

Кратко, что маршрут уже фиксирует:

- Папка: `npm run new-song -- <slug> "Название" "Исполнитель"`. Шаблоны — `docs/methodology/templates/`. Язык `en` в заготовке замените.
- Тяжёлые шаги (Demucs, выравнивание) — как напечатает `song-status`. Локальный Python — только если есть и Python, и ffmpeg. Задание `jobs/<slug>.json` — только если на ветке есть `.github/workflows/pipeline.yml`. Секунды руками не ставить.
- Перед коммитом открытый m4a шифруется: `npm run audio:encrypt -- <slug>`. В git — `content/audio-enc/`, не `public/audio/` и не `work/`.
- Перевод: стадия 6, не быстрее 17 зн/с по времени пения строки. Остаток — в пояснение.
- Код под песню не писать. Язык и письмо уже общие.

Если абзац в `02-audio.md` или `05-alignment.md` предлагает скачать ролик или открыть `/song/<slug>/edit`, верна страница `docs/methodology/README.md` и команда `song-status`.

Отчёт владельцу короткий: какая запись и откуда файл; сколько строк и какие языки; статус тайм-кодов; что осталось в `review`. Песню готовой не называть, пока `review` не пуст или тайм-коды `draft`.
