# T31: независимый аудит репозитория — что сделать эффективнее, по фактам

Исполнитель: Grok (независимый аудитор, не тот, кто это строил). Оркестрация: LL · Tech. Приёмка: LL · Main.

Слова владельца (2026-10-21): «улучшай себя: независимое задание Гроку — исследование, сделать наш репо эффективнее и лучше, не ради галочки, а по факту».

Это **только исследование**. Код, данные, правила и документы проекта в этом шаге не меняются. Меняется один новый файл — `docs/research/repo-audit.md`.

## Зона

- Писать: `docs/research/repo-audit.md`, и при необходимости вспомогательные скрипты подсчёта в `docs/research/repo-audit/` (одноразовые, чтобы цифры можно было перепроверить командой).
- Читать: весь репозиторий, `git log`, `gh run list` / `gh run view` (GitHub CLI авторизован), `ops/usage/` (`ledger/`, `latest.json`, `README.md`), `ops/board.json` и его история (`git log -p ops/board.json`), `ops/handoff/`, `docs/tasks/`, `docs/STATUS.md`, `docs/BACKLOG.md`.
- Push — разрешён только в свою ветку `grok/t31-audit`.

## Что измерить

1. **Что на самом деле происходит.** По `git log`, истории доски, `docs/tasks/`, `ops/handoff/` и запускам GitHub Actions:
   - время от задания (коммит брифа в `docs/tasks/`) до слияния результата в `main` по каждой задаче T1…T30;
   - отклонённые и переделанные проходы (повторные раунды, `rejected` на доске, «раунд N» в отчётах) и их причины;
   - куда ушли токены Claude, Grok и Gemini (`ops/usage/ledger`), и какая трата дала влитый результат, а какая — нет;
   - повторная работа: одно и то же исправление или объяснение дважды, перечитывание одних и тех же документов, устаревшие брифы;
   - сколько владелец ждал нас и сколько мы ждали владельца (раздел «Нужно от вас» на доске, вопросы в отчётах).
2. **Репозиторий глазами нового агента.** Прочитать `AGENTS.md`, `docs/STATUS.md`, `docs/BACKLOG.md`, брифы, `docs/methodology/` как новичок: что устарело, что повторяется, что противоречит одно другому, что слишком длинно; где слабый агент ошибётся. Каждое утверждение — со ссылкой на файл и строку.
3. **Здоровье кода и конвейера.** Время `npm run validate`, `npm run typecheck`, `npm run build` (замерить); покрытие тестами рискованных частей (доказательство синхронизации, проверка последовательности, плеер на iPhone); мёртвый код и скрипты (никто не вызывает); тяжёлые файлы в git (`git count-objects -vH`, самые крупные блобы; `ops/usage/ledger` — больше 14 тыс. строк в месяц: оправдано ли).
4. **Как это делают сильные команды.** Сравнить с практикой команд, которые ведут много агентов, — только то, что подходит под `AGENTS.md`: без новых платных сервисов, всё состояние в репозитории. Источники — ссылками.

## Результат

`docs/research/repo-audit.md`, по-русски, просто:

- **Топ-10 находок**, по убыванию «выигрыш / усилие». У каждой: цифра, которая её доказывает (и как её пересчитать), что исправить, сколько это стоит (часы агента, токены), ожидаемый выигрыш.
- **Список «удалить»** — отдельно: что убрать из репозитория и почему (с цифрой).
- Ничего без измеренной причины. Если цифру получить нельзя, так и написать и не делать вывода.

## Готово, когда

- `docs/research/repo-audit.md` в ветке `grok/t31-audit`, запушен; цифры воспроизводятся командами из документа;
- в отчёте — топ-5 находок одной строкой каждая (для владельца);
- код и документы проекта не тронуты (проверка: `git diff --stat main...grok/t31-audit` показывает только `docs/research/`).
