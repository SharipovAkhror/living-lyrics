# Почему пять базовых строк выпали, когда в замер вошла Alive

Опубликованный выбор — `docs/analysis/bench/attack-chance.json` (коммит `32fab07f`, три песни). Прогон [40192236489](https://github.com/SharipovAkhror/living-lyrics/actions/runs/40192236489), задание `bbf984d8`, лог prove (job `121165533754`). Между этими двумя точками в `attack_chance.py` добавлена только `commit_gate`. Функции замера те же. Пороги в коде не менялись: слово 0,15, строка 0,05, срез от 30 слов, опровержение 0,20 / 0,30 с.

Пять строк входят в `baseline-155.json`, не в тройку `PASS5_EXTRA` (`english-8`, `coda-fa-3`, `shushtari-s2`). База 158 — этот файл плюс тройка.

## Что одно на все песни

Замер читает все песни задания сразу и пишет один `chosen`.

| поле | где считается | опубликовано | прогон 40192236489 |
|---|---|---|---|
| доля K | `choose_with_primaries`, сетка `LINE_SHARES` | 0,25 | 0,25 |
| сетка сдвигов | `SHIFTS` 0,15 / 0,25 / 0,40 и перемешивание | та же | та же, константа |
| порог строки и слова | `LINE_LIMIT` 0,05, `LIMIT` 0,15 | те же | те же |
| порог длины среза | `MIN_WORDS` 30 | 30 | 30 |
| пороги опровержения | `choose_refute` по всем словам сразу | 0,20 / 0,30; 39 из 1050 | 0,20 / 0,30; 50 из 1552 |
| проход строки правила | худший проход постановщика на этой K | 0,0372 | 0,0455 |
| постановщики | один проход на семейство по всем его строкам | mms 0,0185 (127/189), stable-ts 0 (1/4), second 0 (1/9), phoneme 0 (5/6) | mms 0,0312 (200/304), stable-ts 0 (3/6), second 0 (3/14), phoneme 0 (6/9); ни один не исключён |
| объединение | один `admit_union` | `full_or` ложь, проход 0,0372, слов 0,0785, доказано 159, база объединения 109 | `full_or` ложь, проход 0,045454…, слов 0,08687, доказано 257 из 354, база объединения 177, снято `[]` |
| хор | одна пара на правило | spectral / phone | spectral / phone |

Свидетель «один» / «оба» считается по песне и языку (`assign_scopes`), не одной цифрой. Роль фонемы и модель тоже пишутся в срез песни. В объединение они попадают уже как общие участники: член `phone:…` или `fill` несёт строки всех песен, и проход члена — один.

Бит одной строки считается по её словам и пикам её песни. Alive в этот бит не входит. Alive входит в общий проход члена и в общий проход объединения: в знаменателе все строки карты. Поэтому член, который на трёх песнях умещался, на четырёх может получить `within_limit` ложь, хотя биты старых строк те же.

## Что изменилось у срезов

Печатается проход свидетеля «один» (`_slice_chance`, предел 0,15, не 0,05). В обоих выборах режим `slice-one`.

| песня | опубликовано | прогон |
|---|---:|---:|
| i-have-come-alive | 0,0554 | 0,0826 |
| karitas | 0,0508 | 0,0627 |
| one | 0,0639 | 0,0654 |
| alive | нет в файле | 0,0608 |

0,0608 выше 0,05 и ниже 0,15. Код оставляет «один»: `_pick_mode` сравнивает этот проход с 0,15. Предел строки 0,05 к этой цифре не применяется. Отдельный проход строки только Alive лог не печатает. Общий 0,0455 — проход четырёх песен вместе.

Почему сдвинулись срезы старых песен, хотя формула по песне. В логе кэш Actions `stems-htdemucs4-v1-` пуст. У трёх песен стенда `stem_cache.py unpack` пишет «в кэше нет всех четырёх стемов», и Demucs считается заново (12:17–12:37 UTC). У Alive четыре стема восстановлены из артефакта `40144966993`. Пики атаки берутся с этого стема. Промежуточные проходы срезов до передачи и штампа лог не печатает, поэтому долю «новые пики» и долю «передача сдвинула слово» разделить нельзя. Передача в этом прогоне оставлена: 185 против 177. Какие id она перенесла, лог не называет.

По песням опровержение 50 из 1552 не разложено: печатается только сумма. На сколько из 11 новых опровержений пришлись старые песни, из лога не видно.

## Пять строк

`pass_keeps_baseline` разрешает потерю только если в `lost_detail` у строки проход выше 0,05. Объединение напечатало `снято []`: ни одна строка не записана как отказ по пределу строки. Пяти id в доказанных 257 нет. Ворота поэтому и сработали. Защита «базовую строку объединения не снимать» держит базу этого замера (177), а не файл 158.

Опубликованный член строки — по спискам, которые пишет `_apply_union_choice` из имени члена. В новом прогоне у того же имени:

| id | член опубликованного правила | в прогоне |
|---|---|---|
| `arabic-26b` | `fill` (только `line_fill`) | `fill`: 196 строк, проход 0,06006, внутри ложь |
| `coda-fa-1` | `phone:i-have-come-alive:fa:xlsr-53-espeak` | тот же член: 177 строк, проход 0,04655, внутри истина; 177 равно базе объединения, отдельных строк сверх базы этот штамп не добавил |
| `coda-fa-7` | `line_stable` = `medium`; в членах есть `stable:i-have-come-alive:fa:medium` | этот член: 200 строк, проход 0,01952, внутри истина |
| `hildegard-h6-3`, `hildegard-h1-4` | `phone-fill:karitas:la:lv-60-espeak` (`line_fill` и модель `lv-60-espeak`) | тот же член: 198 строк, проход 0,06006, внутри ложь |

`fill` и `phone-fill:karitas:la` при частичном допуске всё ещё предлагают строки по одной. Раз их нет ни в 257, ни в `снято`, остаётся два исхода, и лог их не различает: бит строки на новых пиках уже ложь, либо строку снял предел слова (`word_lost` не печатается). `attack-chance.json` этого прогона не опубликован: ворота вернули стенд.

Заливка огибающей как отдельное правило не оставлена и там, и там: в прогоне 168 против 212, «доказанных строк не больше». В объединение она входит отдельно и на четырёх песнях уже выше 0,05.

Фонема оставлена, поиск greedy, по перебору 201. Это не список ролей по языкам: код печатает срез только при языке `*`.

## Чего лог не закрывает

Нет артефактов выравнивания прогона `39548436423` и нет стемов, которые prove посчитал заново. Нельзя сверить пики, бит каждой из пяти строк и состав `word_lost`. Повторять замер, чтобы это добрать, нельзя: база уже не удержана.
