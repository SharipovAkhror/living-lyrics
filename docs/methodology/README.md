# Как добавить песню

Одна страница-маршрут. После каждого шага запускайте `npm run song-status -- <slug>`. Инструмент печатает таблицу стадий и **одну** следующую команду. Выполните её. Если команда снова `song-status`, абзац над ней — ручной шаг: файлы сами не правятся.

Навык `.claude/skills/add-song/SKILL.md` и раздел «Если вас попросили добавить песню» в `AGENTS.md` ведут сюда. Если старый абзац в файле стадии спорит с этой страницей о том, откуда берётся запись, верна эта страница.

## Что вам дают

Аудиофайл от владельца (в чат) и, возможно, ссылка на официальное видео. Ссылку используйте, чтобы опознать запись и прочитать описание или субтитры. Саму запись с YouTube не скачивайте: из облака её не достать, а в репозиторий она попадает только файлом владельца.

Текста, перевода и тайм-кодов не дают. Их находите и пишете по стадиям ниже. Чего не подтвердили источником или файлом — флаг и пункт в `review`. Пустое поле лучше догадки.

## Как устроены тяжёлые шаги

| Где вы | Запись | Demucs, границы, выравнивание |
|---|---|---|
| Любая среда | Файл кладёт владелец. Агент его не качает | Если на ветке есть `.github/workflows/pipeline.yml`: файл `jobs/<slug>.json`, push, результат приходит коммитом. Сейчас на рабочих ветках этого файла может не быть. `song-status` пишет «отложено» и не просит создавать задание впустую |
| Есть Python и ffmpeg | Скопируйте файл в `work/<slug>/source.m4a` (имя `source.*`, не `.json`). Команду печати `song-status` | Локально: `scripts/pipeline/*.py`, как напечатает `song-status` |
| Нет ffmpeg или Python | Обработать файл нечем. Текст собирайте по стадии 4, секунды не ставьте | Границы секций не выдумывайте. В таблице канона в столбце «с» ставьте «?» |

Перед коммитом открытый m4a шифруется: `npm run audio:encrypt -- <slug>`. В git попадает `content/audio-enc/<slug>/*.m4a.enc`. Каталог `public/audio/` и `work/` не коммитятся. Репозиторий публичный. Ключ `AUDIO_KEY` живёт в `.env.local`, в git его нет.

Шаблоны папки — `docs/methodology/templates/` (в приложении на `/method` их нет, это файлы репозитория). `npm run new-song` копирует их в `content/songs/<slug>/`.

## Правила, которые не меняются от песни к песне

1. Оригинал на экране — то, что поётся, каждый повтор отдельной строкой. Буквы берутся из `canon.md`, не из слуха.
2. Перевод читается, пока строка звучит: не больше 17 знаков в секунду. Считает инструмент по длительности пения (конец последнего слова минус начало первого), не на глаз. Что не поместилось — в пояснение.
3. Пояснение по делу, обычным регистром, без капса.
4. Новая песня не требует нового модуля. Язык — код ISO 639 из `src/data/iso639.ts`. Письмо — код из `SCRIPT_CODES` в `src/data/schema.ts`. Инструмент, которого нет в каталоге, — запись и гравюра по стадии 9, не компонент песни. Палитра уже лежит в `song.json`.

## Стадии

У каждой стадии один и тот же порядок: вход, команды, выход, машинная проверка, типичные ошибки. Подробности — в файле стадии. Код под песню на стадии 10 не пишется.

### 1. Приём — [01-intake.md](01-intake.md)

- Вход: файл владельца или обещание файла, ссылка на официальное видео если она есть, название и исполнитель.
- Команды: `npm run new-song -- <slug> "Название" "Исполнитель"`, затем `npm run song-status -- <slug>`.
- Выход: `content/songs/<slug>/` с `song.json`, `lyrics.json`, `sources.md`, `canon.md`. В `sources.md` есть адрес `https://` или строка `Файл: имя.m4a`. Строка «пустой шаблон» удалена. Язык-заглушка `en` заменён.
- Машинная проверка: в таблице `song-status` строка «приём» — «да». Пока в `review` висит пункт про язык-заглушку `en` и в `languages` только `en`, строка остаётся «нет».
- Типичные ошибки: скачать ролик; оставить `en`; посчитать «Файл: нет» источником; выдумать год, альбом или музыкантов.

### 2. Запись — [02-audio.md](02-audio.md)

- Вход: файл владельца.
- Команды: положить файл в `work/<slug>/source.m4a`. Дальше только то, что печатает `song-status`: `python scripts/pipeline/process_audio.py <slug>`, затем `npm run audio:encrypt -- <slug>`. Раздел «Скачать» в файле стадии для агента не действует, пока оркестратор его не перепишет.
- Выход: `audio.status = ready`, `duration` больше 1 и совпадает с файлом, `provenance.kind = file`, шифр в `content/audio-enc/<slug>/high.m4a.enc`.
- Машинная проверка: строка «запись» — «да».
- Типичные ошибки: коммит открытого m4a; `yt-dlp` без `--skip-download` (это уже скачивание звука); выдумать `gainDb` и `sha256`.

### 3. Структура — [03-structure.md](03-structure.md)

- Вход: обработанная запись.
- Команды: как напечатает `song-status`. Локально это `separate.py`, затем `sections.py`. Через Actions — `jobs/<slug>.json` со стадиями `separate` и `sections`, и только если на ветке есть `pipeline.yml`.
- Выход: в `lyrics.json` вокальные и инструментальные секции. Ключи инструментов из каталога. Неопознанное — `ensemble` и флаг `attribution-unverified`.
- Машинная проверка: строка «структура» — «да» (есть хотя бы одна вокальная строка). Если ни Python с ffmpeg, ни конвейера нет, строка — «отложено», и следующая команда уходит в текст.
- Типичные ошибки: нарисовать границы на слух. После прогона Actions карта голоса лежит в `docs/analysis/<slug>/sections.suggested.json`, черновик распознавания — в `transcript.json` той же папки. Секунды из этих файлов в текст не копируют.

### 4. Текст — [04-text.md](04-text.md)

- Вход: название, исполнитель, официальная страница или субтитры, шаблон `canon.md`.
- Команды: поиск по шагам стадии 4. Субтитры официального видео, если страница не открывается: `yt-dlp --skip-download --write-subs` (звук не качается). Затем правка `canon.md` и `lyrics.json`.
- Выход: эталон с источниками и пометкой «Подтверждено: 1 источник» или «Подтверждено: 2 источника»; последовательность; расхождения. Каждая спетая строка находится в эталоне. Когда строки уже лежат в `lyrics.json`, в `song.json` заполнен `parts` — состав по канону, раздел «Состав песни» в [04-text.md](04-text.md).
- Машинная проверка: `npm run validate -- <slug>` не сообщает, что строка отсутствует в `canon.md`. Строка «текст» в `song-status` — «да». Пока вокальных строк нет, этап не закрыт, даже если в каноне уже есть ссылка. Валидатор предупреждает, если у песни с вокалом нет `parts` или вокальная строка не входит в состав. Строки «состав» в `song-status` нет: таблицу стадий этот шаг не меняет.
- Типичные ошибки: взять текст с сайта «lyrics» как эталон; склеить повторы в одну строку; переписать канон по Whisper.

### 5. Тайм-коды — [05-alignment.md](05-alignment.md)

- Вход: текст, который уже сходится с каноном, и запись.
- Команды: если есть `pipeline.yml` — `jobs/<slug>.json` со стадиями `separate`, `align`, `qa`, как печатает `song-status`. Локально — только когда Python и ffmpeg уже поставили стемы. Секунды руками не двигать. Страницы `/song/<slug>/edit` в проекте нет.
- Выход: у каждого слова `s` и `e`, `timing.status` = `aligned` или `verified`.
- Машинная проверка: строка «тайм-коды» — «да». Пока конвейера на ветке нет, строка — «отложено», публикация не открывается.
- Типичные ошибки: оставить `draft` и назвать песню готовой; растянуть слово «чтобы красиво легло».

### 6. Перевод — [06-translation.md](06-translation.md)

- Вход: строки с измеренной или черновой длительностью. Если тайм-коды ещё черновик, скорость всё равно считается по тем `s`/`e`, которые уже лежат в строке. Черновик не повод писать простыню.
- Команды: подстрочник, смысл, строка для чтения, остаток в пояснение. Проверка: `npm run song-status -- <slug>` и `npm run validate -- <slug>`.
- Выход: у каждой вокальной строки `tr.ru`, скорость не выше 17 зн/с.
- Машинная проверка: строка «перевод» — «да». Валидатор предупреждает только выше 20 зн/с, при слове из запретного списка, при капсе и если у строки с `em` нет пары `**…**`.
- Типичные ошибки: подстрочник на экран; мерить паузу до следующей строки; считать скорость на глаз.

### 7. Пояснения — [07-comment.md](07-comment.md)

- Вход: фрагменты `canon.md` и инструментальные секции.
- Команды: одно пояснение на фрагмент — автор, форма, контекст — у первой его секции или первой строки. У проигрыша поле `note`. Секция только с `voice` или `choir` ничего не требует. Затем `song-status`.
- Выход: у каждого спетого фрагмента есть это пояснение. У проигрыша есть `note`. Пояснение отдельной строки — только если перевод не передал термин, игру слов или аллюзию. Строка с `em` пояснения не требует: пара `**…**` уже стоит в переводе.
- Машинная проверка: строка «пояснения» — «да». Машина не ищет строки, где перевод что-то потерял: это чек-лист в файле стадии. Валидатор предупреждает, если в `comment` попали слова «субтитр», «титр», «транскрипт», whisper, «распознава», «слухом», «ухом», «не проверен», «реплика».
- Типичные ошибки: пустое пояснение к каждой секции и к каждому `em`; редакторская заметка в `comment`; строка из одних знаков вместо секции `voice`.

### 8. Транскрипция — [08-transliteration.md](08-transliteration.md)

- Вход: строки с письмом `Arab` или `Aran`.
- Команды: заполнить `translit` по таблицам стадии 8.
- Выход: кириллица как поётся.
- Машинная проверка: `npm run validate -- <slug>` не предупреждает о пустом `translit`. Строка «транскрипция» — «да». Латиница и кириллица транскрипцию не требуют: пустое поле у них — норма.
- Типичные ошибки: научная транслитерация с диакритикой; транскрипция «как в словаре», а не как в записи.

### 9. Инструменты — [09-instruments.md](09-instruments.md)

- Вход: то, что слышно в проигрыше, и каталог `src/instruments/list.ts`.
- Команды: ключи в `instruments`. Нового ключа нет в каталоге — рецепт гравюры в файле стадии, не новый модуль песни. Пока ключ не опознан: `ensemble` и `attribution-unverified`.
- Выход: все ключи есть в каталоге.
- Машинная проверка: строка «инструменты» — «да», валидатор не ругает неизвестный ключ.
- Типичные ошибки: восемь ключей «на всякий случай»; имя музыканта без буклета или титра.

### 10. Сцена — [10-choreography.md](10-choreography.md)

- Вход: готовые данные стадий 3–8.
- Команды: нет. `em` и `br` уже поля строки. Поле `fx` не заполнять.
- Выход: ноль файлов в `src/`.
- Машинная проверка: строка «сцена» всегда «да».
- Типичные ошибки: компонент, хук или страница под одну песню.

### 11. Проверка — [11-qa.md](11-qa.md)

- Вход: песня, у которой предыдущие строки таблицы закрыты или честно отложены.
- Команды: `npm run validate -- <slug>`, для финала `npm run validate -- --strict <slug>`, `npm run typecheck`.
- Выход: пустые `review` и флаги. Предупреждения на чужих старых песнях не стирайте вместе со своим текстом.
- Машинная проверка: строка «проверка» — «да».
- Типичные ошибки: снять `text-unverified`, не открыв источник; обнулить `review`, не ответив на вопрос.

### 12. Публикация — [12-publish.md](12-publish.md)

- Вход: строки 1–11 закрыты, тайм-коды не `draft`.
- Команды: как напечатает `song-status`: `git add content/songs/<slug> content/audio-enc/<slug>`.
- Выход: коммит в свою ветку. В `main` не сливать. Push — только если задание это прямо разрешает.
- Машинная проверка: строка «публикация» — «да», и команда называется сама.
- Типичные ошибки: `git add public/audio`; коммит `work/`; коммит при `timing.status = draft`.

## Статусы

- `timing.status`: `draft` (оценки или пусто) → `aligned` (выравнивание доказало строки) → `verified` (владелец прослушал запись; кнопка «Не совпадает» ничего не оставила, либо отметки уже разобраны). Редактора тайм-кодов нет. Пока стоит `draft`, сайт не заливает слова по времени.
- Флаги строк и секций: `text-unverified`, `timing-draft`, `translation-draft`, `comment-draft`, `attribution-unverified`. Снимайте флаг после проверки, не до неё.
- `review` в `song.json` — открытые вопросы обычными фразами. Песня готова, когда список пуст, флагов нет, тайм-коды не черновик и `npm run validate -- --strict <slug>` проходит.

Порядок в таблице `song-status` такой: приём, запись, структура, текст, тайм-коды (если конвейер есть), перевод, пояснения, транскрипция, инструменты, проверка. Пока конвейера нет, текст и перевод идут при черновых секундах, а публикация всё равно ждёт выравнивания.
