# 12. Публикация

**Параллельно.** Нет.

**Вход.** `npm run song-status -- <slug>` показывает строки 1–11 закрытыми, а «тайм-коды» — «да» (`aligned` или `verified`). Пока статус `draft`, инструмент оставляет публикацию в «рано» и не даёт эту стадию следующей командой. Секунды руками не проставляйте, чтобы обойти ожидание. Прослушивание владельцем этой командой не запускается: оно между проверкой и решением оркестратора слить ветку.

**Команды.** Сначала проверка, затем то, что напечатает `song-status`:

```bash
npm run validate -- --strict <slug>
npm run typecheck
npm run audio:encrypt -- <slug>
git add content/songs/<slug> content/audio-enc/<slug> docs/analysis/<slug> docs/analysis/translation/<slug>.md
git commit -m "Add <Title>: text, translation, commentary, timing (<status>)"
```

Шифр стадию 2 не держит. Пока ключа нет, таблица показывает «шифр: ждёт ключа», и текст с видео идут дальше. Здесь, перед коммитом, шифр обязателен. Если открытый `high.m4a` есть, а `content/audio-enc/<slug>/high.m4a.enc` нет, `song-status` печатает `npm run audio:encrypt -- <slug>` — когда `AUDIO_KEY` уже в `.env.local` (64 шестнадцатеричных знака). Без ключа коммит записи не начинается: открытый файл в команду `git add` не попадает. В git ключ не кладите.

Команда `git add`, которую печатает `song-status`, называет только существующие пути: папка песни, шифр, и если они есть — `docs/analysis/<slug>` и `docs/analysis/translation/<slug>.md`. Несуществующий путь в команду не попадает.

**Выход.** Коммит в свою ветку: папка песни, шифр `content/audio-enc/<slug>/*.m4a.enc`, разбор в `docs/analysis/<slug>/` и досье перевода, если они есть. Открытого m4a в коммите нет. Каталога `work/` в коммите нет. В `main` ветку не сливают: это шаг оркестратора.

**Машинная проверка.** После коммита `git status` не показывает `public/audio` и `work`. `song-status` до коммита писал строку «публикация» как «да» и одну команду `git add`.

## Что коммитится

Репозиторий публичный. Открытая запись в него не входит: `public/audio/**/*.m4a` игнорируется. Слушатель получает файл после расшифровки на сборке, ключ живёт в переменных среды.

В коммит песни входят:

- `content/songs/<slug>/` — `song.json`, `lyrics.json`, `canon.md`, `sources.md`;
- `content/audio-enc/<slug>/` — шифр высокой дорожки и, если скрипт его сделал, облегчённой;
- `docs/analysis/<slug>/` — реплики, кадры, сведение, вступления, если папка есть;
- `docs/analysis/translation/<slug>.md` — досье перевода, если файл есть.

Не входят:

- `public/audio/`, `work/`, `.env`, `.env.local`;
- веса моделей выравнивания;
- `jobs/<slug>.json`, если задание уже отработало и файл должен был исчезнуть.

Сообщение коммита — английская фраза, как в `git log`: что за песня и какой статус тайм-кодов. Серия мелких коммитов по стадиям лучше одного мешка, если так устроена ветка.

В `main` эту ветку сами не сливайте. Push — только если задание, которое вам выдали, прямо разрешает push. Исполнитель в чужой ветке чужую историю не переписывает.

Новая гравюра инструмента, если она понадобилась по стадии 9, коммитится вместе с каталогом (`src/instruments`, `scripts/art`), отдельным осмысленным коммитом, не внутри текста песни.

## Деплой

Сайт собирается `npm run build` (валидатор, типы, Vite) и выкладывается с `main`. Пароль — `middleware.ts` и переменные `SITE_PASSWORD`, `AUTH_SECRET` в настройках площадки, не в репозитории. Ссылка на момент: `/song/<slug>?t=95`.

После того как запись попала на площадку, откройте песню на телефоне и пройдите её в наушниках. Замечание — новый пункт `review` и новый коммит, не правка уже опубликованного тайм-кода «на глаз».

## Типичные ошибки

- `git add public/audio` или `git add -A`, пока в дереве лежат `work/` и открытый m4a.
- Написать в инструкции, что аудио едет в приватный репозиторий или в Git LFS. Так было в старой редакции этой страницы. Сейчас шифр в публичном репозитории.
- Коммитить при пустом `canon.md` или при `timing.status = draft`.
- Залить `AUDIO_KEY` в файл, который не игнорируется.
