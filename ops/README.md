# Ход работы

- `board.json` — доска: что идёт сейчас, что нужно от владельца, прогресс песен, путь «до новых песен», последние передачи работы. Обычный JSON, читает кто угодно. Обновляет тот, кто ведёт работу, после каждого шага (выдал задание, принял, решение владельца) и коммитит.
  Поля: `updated` (ISO, UTC), `headline`, `tasks[]` (`id`, `section`: `you` | `now` | `done` | `later`, `agent`, `status`, `title`, `what`, `now`, `next`, `worktree`), `songs[]` (группы строк: доказано / поставлено / всего), `roadmap` (шаги с весом и долей готовности), `feed[]` (не больше 8, новые сверху), `models`.
- `usage/` — учёт расхода исполнителей (Grok, Gemini), см. `usage/README.md`.
- `agents/` — помощники для Grok Build: `grok_status.py` (кто что делает по папкам `../living-lyrics-wt/*`), `last_report.py <папка>` (последний отчёт), `watch_log.py <папки…>` (ждать, пока кто-то закончит ход), `publish_live.py` (выкладывает живое состояние исполнителей в ветку `live`, см. ниже).
- **Порядок в ветках:** на GitHub включено удаление ветки после вливания PR (`delete_branch_on_merge`, решение владельца 2026-10-20). Ветки, влитые без PR, так не удаляются — их убирает тот, кто влил (позже — ночная проверка порядка, `docs/research/agent-system.md`, шаг 3).
- `agents/grok_exec.mjs` — запуск Grok для исполнителей: в безголовых прогонах (`-p`) убирает инструменты, которые нашим задачам не нужны (видео, правка картинок, расписание, workflow, отзывы; описания инструментов уходят с каждым вызовом модели: 56 → 32 КБ). Остальные вызовы `grok` проходят как есть. Мост Grok берёт его через переменную: `GROK_BINARY="node C:/Users/User/Documents/GitHub/living-lyrics/ops/agents/grok_exec.mjs" node <мост>/grok-bridge.mjs run …` — ставить её в каждой команде запуска (в настройки Claude её не вписать: это изменение самих настроек Claude, автопроверка его запрещает). В `~/.grok/config.toml` выключено чтение хуков, навыков и MCP Claude (`[compat.claude]`): сбои хуков Orca и лишние описания (аудит LL · Ops, `docs/research/setup-audit-2026-10-22.md`).
- `agents/station_tick.py` — раз в 2 минуты из мода на Станции: подтягивает главную папку репозитория к `origin/main` (только перемотка и только если ничего, изменённого здесь, не менялось наверху; чаты пушат из worktree, и без этого доска и сам мод на диске отстают), и отдаёт моду чаты из реестра с их состоянием и идущие запуски GitHub Actions — они попадают в живое состояние (`live`) и в сводку `/dashboard`.
- `agents/keep_chats.py` — поднимает рабочий чат, который демон Claude остановил после 8 часов простоя (`claude respawn`); его раз в 10 минут запускает мод на Станции (`docs/process/chat-rotation.md`, «Фоновые процессы»).
- `dashboard-mod/` — мод Claude Code: строка над полем ввода, панель Dashboard и карточка в чате по слову `dashboard`. Это окно в `board.json`: в сессии, открытой в репозитории, он читает файл с диска, в любой другой — берёт доску и живое состояние из GitHub (репозиторий публичный), так что работает на любом компьютере. Ответ на `/dashboard` (или слово «дашборд», «штаб») — одна картинка: та же страница, что и боковая панель (`dashboard-mod/panel.html`), снятая в PNG через Playwright из репозитория (`dashboard-mod/card/render.mjs`). Станция рисует её заранее при каждой записи панели (`%LOCALAPPDATA%\ll-dashboard\dashboard.png`, отметка в `card.json`), поэтому ответ только отправляет готовый файл. Боковая панель — артефакт claude.ai: мод на Станции пишет её документ `dashboard/now` сам (владелец разрешил 2026-10-21; разрешение — хук `tool.check`, только для своих записей в этот документ). `node ops/dashboard-mod/card/render.mjs <state.json> <out.png> [--light]` перерисует картинку вне чата. Исходник мода один — эта папка; репозиторий — витрина плагинов (`.claude-plugin/marketplace.json`: витрина `living-lyrics`, плагин `ll-dashboard`).

## Машины

Так их называют в разговорах, документах и отчётах агентов:

| Название | Что это | Что там идёт |
|---|---|---|
| **Станция** | домашний ПК владельца, Windows (`WIN-SLPJLK81BLJ`), папка `C:\Users\User\Documents\GitHub\living-lyrics` | всё: главная сессия Claude Code, Grok и Gemini (`../living-lyrics-wt`), сбор расхода, выкладка живого состояния в `live`. Оркестратор |
| **Ноутбук** | ноутбук владельца | только окно: сессии Станции через удалённое подключение (Remote Control) или свои сессии, в которых мод читает всё из GitHub |
| **Облако** | сессии claude.ai/code и GitHub Actions | облачные сессии и тяжёлые шаги конвейера; мод там не работает |
| **Телефон** | телефон владельца | окно в сессии Станции |

Если вы пишете с Ноутбука или Телефона в сессию Станции, команды выполняются на Станции.

### Настройки каждого устройства

Мод Dashboard при каждом запуске сессии сверяет `~/.claude/settings.json` этого устройства (или `$CLAUDE_CONFIG_DIR/settings.json`) с коротким списком `USER_SETTINGS` в `ops/dashboard-mod/hooks/register.tsx` и дописывает ключ, только если его нет или он другой; остальное в файле не трогает. Сейчас в списке одно: `cleanupPeriodDays: 36500` — история чатов не удаляется (решение владельца 2026-10-20: хранить вечно, во всех проектах). Новая настройка для всех устройств — одна строка в `USER_SETTINGS` и повышение версии мода.

На новом устройстве нужно одно: чтобы на нём стоял мод (раздел «Привязка к аккаунту и другие устройства»; через витрину, подключённую к аккаунту claude.ai, он приезжает сам после входа). Дальше настройки ставятся сами при первом запуске сессии и больше не требуют внимания. Проверка: в `~/.claude/settings.json` есть `"cleanupPeriodDays": 36500`.

Что хранит этот ключ: транскрипты сессий этого устройства (`~/.claude/projects/…`), в том числе архивных чатов. Сессии с Remote Control и облачные сессии хранятся ещё и на claude.ai.

## Откуда мод берёт данные

| Что | Машина-оркестратор (рядом лежит `../living-lyrics-wt`, сессия в главной папке репозитория) | Любое другое место |
|---|---|---|
| Доска и расход | файлы `ops/board.json`, `ops/usage/latest.json` с диска | `raw.githubusercontent.com/SharipovAkhror/living-lyrics/main/ops/…` раз в 2 минуты |
| Живое состояние Grok и Gemini | считает `dashboard-mod/hooks/agents_live.py` раз в 30 секунд | `ops/live.json` из ветки `live` (`…/refs/heads/live/ops/live.json`) раз в 2 минуты |
| Сбор расхода `ops/usage/collect.py` | раз в 10 минут | не запускается |

Raw-адреса GitHub кэширует до пяти минут: на другом устройстве состояние отстаёт на несколько минут.

## Живое состояние через GitHub

Мод на машине-оркестраторе при каждой смене состояний (кто работает, остановился, закончил, кто смотрит видео) и раз в 10 минут вызывает `python ops/agents/publish_live.py <репозиторий>`. Скрипт:

- берёт состояние у `agents_live.py` (или из stdin: `… | python ops/agents/publish_live.py --stdin`);
- сравнивает «подпись» (имена, состояния, модели; минуты и шаги в неё не входят) с прошлой выложенной — она лежит в `.git/ll-live.json` главной папки; та же подпись — ничего не делает. Раз в 10 минут выкладывает и без перемен (сердцебиение), даже когда никто не работает, чтобы читатель отличал тихую машину от выключенной;
- собирает коммит командами git «plumbing» (ни одна ветка, индекс и файлы главной папки не затрагиваются) и принудительно записывает его в ветку `live`: в ней один коммит без родителей, внутри `ops/live.json` (`at` — время записи, `grok[]`, `gemini[]`), `vercel.json` и `README.md`. `main` не засоряется, история `live` не растёт.

Мод на других устройствах прибавляет к минутам время, прошедшее с `at`; состояние старше 45 минут считает устаревшим и показывает карточки доски без него (машина выключена или нет сети).

**Сигнал «Станция не отвечает»** (`.github/workflows/station-watch.yml`): GitHub раз в 15 минут читает `at` в `ops/live.json` ветки `live`. Старше 30 минут — открывает одну задачу (issue) с меткой `station-down`, назначает её владельцу (письмо и уведомление GitHub на телефон); свежее — пишет в неё «снова на связи» и закрывает. Одно уведомление на одно выключение. Расписание GitHub запаздывает на 5–20 минут, поэтому сигнал приходит через 30–50 минут после выключения.

**Vercel не собирает `live`:** в `vercel.json` главной ветки — `git.deploymentEnabled: { "live": false }`, и тот же запрет лежит в `vercel.json` самой ветки `live`. Проверено по списку деплоев проекта: первая выкладка вышла без читаемого `vercel.json` и дала один сбойный деплой (остался в истории Vercel), следующая — с ним, деплоя не создала. Раннеры GitHub Actions на `live` не стартуют: у `pipeline.yml` фильтр по `jobs/*.json`, других файлов в ветке нет.

### Переезд оркестрации в облако

Мод и `publish_live.py` не зависят от компьютера владельца, пока есть кому производить JSON вида `{"grok":[{"name","state","minutes","step","model"}],"gemini":[{"slug","minutes"}]}` (`state`: `working` | `stalled` | `finished` | `none`). Когда оркестратор переедет в облако: заменить `agents_live.py` источником оттуда (PowerShell и `~/.grok` нужны только нынешней машине), вызывать `publish_live.py --stdin` из облака (нужны `git push` в этот репозиторий и сеть). Мод на машине владельца менять не придётся: когда рядом не будет `../living-lyrics-wt`, он сам перейдёт на чтение из `live`.

## Один источник мода на компьютере владельца

Витрина `living-lyrics` подключена как локальная папка (`claude plugin marketplace add C:/Users/User/Documents/GitHub/living-lyrics`). Относительный плагин `./ops/dashboard-mod` грузится на месте из этой папки: правки видны после `/reload-plugins`. Номер версии (`ops/dashboard-mod/.claude-plugin/plugin.json`, сейчас 0.10.1) нужен установкам с GitHub: без повышения они не обновятся. Главная папка репозитория должна стоять на `main`: плагин читает её файлы как есть.

Переключение со старой копии (папка разработки `C:\Users\User\.claude\dev-mods\<id сессии>\ll-dashboard` живёт в одной сессии) делается один раз, в момент, который выбирает владелец:

```bash
claude plugin install ll-dashboard@living-lyrics      # user scope: все сессии на этом компьютере
# затем удалить папку dev-mods\377eb041-697f-421c-bab9-46263b7d6c25\ll-dashboard
# и в открытых сессиях: /reload-plugins
```

Две одноимённые копии не ломают друг друга, но [мод одного имени грузит только одна](https://code.claude.com/docs/en/plugins/loading#hooks-when-two-enabled-plugins-share-a-name), поэтому старую убирают сразу. Проверка: `/plugin` пишет `1 mod active · ll-dashboard`, `claude plugin list` показывает `ll-dashboard@living-lyrics` включённым.

## Привязка к аккаунту и другие устройства

Источники: [loading#synced-plugins](https://code.claude.com/docs/en/plugins/loading#synced-plugins), [install](https://code.claude.com/docs/en/plugins/install#plugins-from-your-claude-ai-account), [claude.com/docs/plugins/overview](https://claude.com/docs/plugins/overview).

- **Витрину можно подключить к аккаунту claude.ai.** claude.ai → Customize → Plugins → Add → Add marketplace → `SharipovAkhror/living-lyrics` (публичный GitHub-репозиторий подходит; можно включить «Sync automatically» — витрина сама подтягивается из репозитория). Другой путь: Add → Upload plugin (zip папки `ops/dashboard-mod`). Ограничения по плану в документации названы только для Team и Enterprise (владелец организации решает, что могут добавлять участники); для личного аккаунта ограничений нет, но я не проверял это сам: загрузку делает владелец.
- **Что приезжает.** Включённый в аккаунте плагин скачивается как `ll-dashboard@synced` при запуске терминального Claude Code со входом через claude.ai (версия 2.1.273+); затем `/reload-plugins` или новый запуск. Условия: вход именно через claude.ai (не токен и не `apiKeyHelper`), не `--bare` и не `--safe-mode`. Механизм на этом аккаунте работает: в `claude plugin list` уже есть `data@synced`.
- **Одноимённая копия побеждает синхронизированную** (в порядке разрешения имён `@synced` стоит последним). На ПК, где `ll-dashboard@living-lyrics` стоит из витрины, синхронизированный не загрузится — так и задумано.
- **Не подтверждено документацией — проверить после загрузки.** Грузятся ли *моды* (`hooks/hooks.json` с `modules`) из синхронизированных плагинов: в описании синхронизации названы навыки, агенты, hooks, MCP и LSP. Проверка за полминуты: на ноутбуке после синхронизации `/plugin` должен написать `1 mod active · ll-dashboard`. Не написал — ставить из витрины, как в разделе «Ноутбук», это надёжно.
- **Локальные сессии вкладки Code в приложении.** Про синхронизацию плагинов в них документация приложения молчит (о синхронизации сказано для терминальных сессий и Cowork). Зато терминал и локальные сессии приложения на одном компьютере читают одни файлы настроек ([install, «Choose an install scope»](https://code.claude.com/docs/en/plugins/install#choose-an-install-scope)), поэтому плагин, поставленный в user scope из витрины, работает и там, и там.
- **Рабочие чаты в приложении — без полосы и панели мода (проверено 2026-10-23).** Рабочие чаты — фоновые процессы под демоном. Приложение и телефон показывают их через Remote Control. Мод в таком чате работает: хуки, напоминание о ротации, `keep_chats`, запись живой панели. Но полоса над полем ввода и боковая панель рисуются только в окне, где запущен сам процесс. Клиент Remote Control их не показывает: строку состояния он тоже не рисует, запрос [anthropics/claude-code#83425](https://github.com/anthropics/claude-code/issues/83425) закрыт как «не планируется». Поэтому мод видно только в локальной сессии приложения. Нашими средствами это не исправить. Что видно в любом рабочем чате: карточка мода по слову `dashboard` и живая панель на claude.ai (`https://claude.ai/artifact/UxZtjaBuWo2eDXW3fSC6tp`; можно закрепить в боковой панели приложения).

### Ноутбук

Надёжный путь, не зависящий от синхронизации: в приложении «+» у поля ввода → Plugins → Add plugin; если нужной витрины в списке нет — один раз в терминале ноутбука

```bash
claude plugin install ll-dashboard --marketplace SharipovAkhror/living-lyrics
```

(нужна версия 2.1.292+; команда сама добавит витрину и поставит плагин в user scope). Мод на ноутбуке берёт доску и живое состояние из GitHub, больше ничего не нужно. Если мод не появился: `claude plugin list` (виден ли), `/plugin` → вкладка Errors, `claude --version` (моды требуют 2.1.287+, в приложении 2.1.286+). Не помогло — пришлите вывод `claude plugin list` и текст из Errors.

### Веб-версия (claude.ai/code) и iOS

Честно: облачная сессия **не загружает ни личные плагины, ни включённые в `.claude/settings.json` репозитория** ([cloud-environments](https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup)); в неё приезжают только навыки аккаунта и всё, что лежит в репозитории (`CLAUDE.md`, `.claude/skills/`). К тому же интерфейс мода в облачной сессии не рисуется вовсе ([где работают моды](https://code.claude.com/docs/en/plugins/mods/overview#where-mods-run)). Панели Dashboard в браузере не будет ни при каком плагине.

Лучшее доступное: попросить «что на доске?» — облачная сессия клонирует репозиторий, читает `ops/board.json` и живое состояние из ветки `live` (`git fetch origin live && git show FETCH_HEAD:ops/live.json`). Навык dashboard на эти две команды (папка .claude/skills/dashboard) в облаке заработает как есть; он вне зоны задачи T23 и не создан — решение владельца. С телефона: сессия на ПК через Remote Control показывает карточку мода в чате (слово `dashboard`). iOS-приложение владелец не ждёт.
